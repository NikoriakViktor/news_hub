    Колекції: адреси, фільтри, сортування, пагінація¶

    Проблема¶

    Ендпоінт списку — найнавантаженіший і найнебезпечніший в API. Він повертає багато рядків, приймає параметри від клієнта і з часом обростає фільтрами. Тут легко припуститися трьох помилок, які на маленькій базі не видно:

    • сторінки «з'їжджають»: користувач бачить ту саму новину двічі або пропускає якусь;
    • глибокі сторінки гальмують: чим далі гортаєш, тим повільніше;
    • параметри сортування стають дірою: клієнт підставляє в запит що завгодно.

    Ментальна модель¶

    GET /posts?category=news&sort=-id&limit=10&cursor=eyJpZCI6IDk5OTk5OH0=
    └─┬─┘ └──────┬──────┘ └──┬──┘ └───┬──┘ └──────────────┬─────────────┘
   колекція   фільтр   сортування  розмір      звідки продовжити
    • Шлях називає ресурс: колекцію (/posts) або елемент (/posts/42), іноді вкладену колекцію (/posts/42/comments).
    • Рядок запиту уточнює, яку частину колекції віддати: фільтр, порядок, сторінка.
    • Фільтр, сортування й пагінація виконуються в базі (WHERE, ORDER BY, LIMIT), а не в Python після SELECT *.

    Адреси й вкладені ресурси¶

    Правило Приклад Чому
    колекція — іменник у множині /posts, /api/news найпоширеніша домовленість; головне — однаково в усьому API
    елемент — колекція + id /posts/42 —
    вкладений ресурс — лише коли він не існує без батька /posts/42/comments коментар належить посту
    не глибше одного рівня /comments/7, а не /users/1/posts/42/comments/7 довгі адреси крихкі й дублюють зв'язки, які вже є в даних
    коса риска — однаково скрізь без неї інакше 307 замість даних (HTTP-запит і відповідь)

    Однина (/post/42) теж трапляється, зокрема в книжках про FastAPI: в англійській є неправильні форми множини, і хтось обирає однину, щоб їх обійти. Обидва варіанти робочі. Погано лише змішувати їх в одному API.

    Вкладена адреса — не перевірка прав. GET /posts/1/comments/2 має повернути коментар 2, лише якщо він справді належить посту 1:

    pagination_app.py (фрагмент)
    comment = db.scalar(select(Comment).where(Comment.id == comment_id, Comment.post_id == post_id))
if comment is None:                        # чужий коментар — теж 404, а не дані іншого поста
    raise HTTPException(404, "Comment not found")

    GET /posts/1/comments/1 → 200 {'id': 1, 'post_id': 1, 'text': 'до поста 1'}
GET /posts/1/comments/2 → 404 {'detail': 'Comment not found'}

    Якщо шукати лише за comment_id, другий запит віддав би коментар іншого поста. Це IDOR (Insecure Direct Object Reference): доступ до чужого об'єкта простим перебором id.

    Фільтр і сортування¶

    pagination_app.py (фрагмент)
    SORT_COLUMNS = {"id": Post.id, "title": Post.title}                     # білий список полів


@app.get("/posts")
def list_posts(
    db: Db,
    category: str | None = None,
    sort: Literal["id", "-id", "title", "-title"] = "-id",               # «-» — за спаданням
    offset: Annotated[int, Query(ge=0)] = 0,
    limit: Annotated[int, Query(ge=1, le=100)] = 10,
) -> list[PostOut]:
    column = SORT_COLUMNS[sort.lstrip("-")]
    order = column.desc() if sort.startswith("-") else column.asc()
    tiebreak = Post.id.desc() if sort.startswith("-") else Post.id.asc()  # однакові title — порядок за id
    stmt = select(Post).order_by(order, tiebreak).offset(offset).limit(limit)
    if category:
        stmt = stmt.where(Post.category == category)
    return [PostOut.model_validate(p) for p in db.scalars(stmt)]

    Три рішення в цих рядках:

    • Literal замість str — FastAPI сам відхиляє все, чого немає в списку, а /docs показує допустимі значення. Ім'я поля від клієнта ніколи не потрапляє в SQL як текст.
    • le=100 на limit — клієнт не може попросити мільйон рядків одним запитом.
    • Друге поле сортування (id) — якщо в кількох постів однаковий title, база може віддати їх у різному порядку від запиту до запиту, і на межі сторінок рядки губляться або повторюються. Унікальний «вирівнювач» робить порядок однозначним.
    {'sort': 'title; DROP TABLE posts'} → 422 ["Input should be 'id', '-id', 'title' or '-title'"]
{'limit': 1000} → 422 ['Input should be less than or equal to 100']

    Пагінація: offset чи курсор¶

    offset + limit курсор (keyset)
    запит до бази ORDER BY id DESC LIMIT 10 OFFSET 900000 WHERE id < :last_id ORDER BY id DESC LIMIT 10
    перейти на сторінку N так ні, лише «далі» (і «назад», якщо зробити)
    швидкість глибоких сторінок падає: база читає й відкидає offset рядків стала: індекс одразу веде до потрібного місця
    вставка чи видалення між сторінками рядки зсуваються: дублікати або пропуски стабільно
    загальна кількість сторінок легко (COUNT(*)) зазвичай не показують
    де доречний адмінки, таблиці з номерами сторінок, невеликі колекції стрічки, нескінченна прокрутка, експорт, великі таблиці

    Курсор — /posts/feed. Клієнт отримує next_cursor і передає його в наступний запит. Усередині — id останнього показаного запису в base64, але для клієнта це непрозорий рядок: його формат можна змінити, не ламаючи клієнтів.

    pagination_app.py (фрагмент)
    stmt = select(Post).order_by(Post.id.desc()).limit(limit + 1)        # +1: чи є наступна сторінка
if cursor:
    stmt = stmt.where(Post.id < decode_cursor(cursor))
rows = list(db.scalars(stmt))
items, more = rows[:limit], len(rows) > limit
return Page(items=[PostOut.model_validate(p) for p in items],
            next_cursor=encode_cursor(items[-1]) if more else None)

    pagination_demo.py на таблиці з мільйоном постів (SQLite):

    Таблиця: 1,000,000 постів

1. Новий пост між сторінками (новіші першими)
  offset: сторінка 1 [1000000, 999999, 999998] → сторінка 2 [999998, 999997, 999996]
  cursor: сторінка 1 [1000000, 999999, 999998] → сторінка 2 [999997, 999996, 999995]

2. Глибока сторінка: та сама позиція, різні способи
  offset=0           5.4 мс  перший id 1000001
  offset=900000    807.8 мс  перший id 100001
  cursor            5.1 мс  перший id 100001
    1. Зсув. Поки користувач читав першу сторінку, з'явився новий пост. Усі рядки зсунулись на одну позицію, і offset=3 знову показав 999998. Курсор продовжив «після 999998», і йому байдуже, що з'явилось нагорі.
    2. Глибина. Та сама сторінка: через offset — 808 мс (база перебрала 900 000 рядків, щоб їх відкинути), через курсор — 5 мс, як перша сторінка. Час offset росте з номером сторінки, тож між запусками він різний (590–810 мс у наших вимірах), а курсор стабільно швидкий.

    Курсор вимагає унікального й упорядкованого ключа. Для сортування за неунікальним полем (дата, заголовок) курсор — пара (поле, id), а умова — WHERE (published, id) < (:published, :id).

    У News Hub¶

    GET /api/news (крок 2, з кроку 3 — у SQL):

    stmt = select(NewsRow).order_by(NewsRow.id).offset(skip).limit(limit)
    • фільтри — category, source, lang (Literal["uk", "ru"]), з кроку 7 — ai_category, sentiment; усі в WHERE;
    • пагінація — skip/limit, limit від 1 до 1000;
    • порядок — за id за зростанням: нові новини додаються в кінець, тож вставка під час гортання сторінки не зсуває. Зсув з'явиться, якщо перевернути порядок на «новіші першими» — тоді стрічці потрібен курсор;
    • пошук q — title.icontains(q, autoescape=True): % і _ від клієнта — звичайні символи, а не шаблон SQL.

    Типові помилки¶

    Помилка Наслідок Як правильно
    select(Post) усієї таблиці, потім items[offset:offset + limit] у Python пам'ять і час ростуть з розміром таблиці OFFSET/LIMIT або курсор у SQL
    limit без верхньої межі один запит вивантажує всю таблицю Query(ge=1, le=100)
    sort_by: str, підставлений у SQL-рядок SQL-ін'єкція Literal[...] + словник полів
    сортування лише за неунікальним полем на межі сторінок рядки губляться й повторюються друге поле — id
    offset для стрічки «новіші першими» дублікати при нових записах, повільні глибокі сторінки курсор
    вкладений ресурс шукають лише за власним id IDOR: доступ до чужого через перебір умова і за id батька, і за власним
    курсор — відкритий ?last_id= клієнти залежать від формату, перебирають id непрозорий рядок; недійсний — 400

    Налагодження¶

    • echo=True в create_engine показує SQL: шукай LIMIT/OFFSET або WHERE id < — якщо їх немає, пагінація в Python.
    • Повільна глибока сторінка — EXPLAIN QUERY PLAN (SQLite) або EXPLAIN ANALYZE (PostgreSQL): для курсора має бути пошук за індексом, а не перебір.
    • Дублікати між сторінками — перевір, чи порядок однозначний (є id у ORDER BY) і чи не змінились дані між запитами.

    Безпека¶

    • Верхня межа limit — захист від DoS: без неї кілька запитів з limit=1000000 займуть базу й пам'ять процесу.
    • Білий список полів сортування й фільтрації — ніякого getattr(Model, sort_by) і f-рядків у SQL.
    • Перевірка належності у вкладених ресурсах — WHERE id = :id AND post_id = :post_id, і 404 на чуже.
    • Пошук з LIKE — екранувати % і _ (autoescape=True), інакше клієнт може запускати дорогі шаблони на всю таблицю.

    Питання¶

    1. Чому фільтр, сортування й пагінацію роблять у SQL, а не в Python?
    2. Що побачить користувач на другій сторінці offset-пагінації, якщо між запитами з'явився новий запис (сортування «новіші першими»)? А з курсором?
    3. Чому глибока сторінка через offset повільна, а через курсор — ні?
    4. Навіщо id другим полем сортування?
    5. Чому в News Hub skip/limit не дає дублікатів при нових новинах?
    6. Що перевірити в GET /posts/{post_id}/comments/{comment_id}?
    Відповіді
    1. Інакше з бази читається вся таблиця: пам'ять і час ростуть разом з даними.
    2. З offset — останній запис першої сторінки ще раз (усе зсунулось на одну позицію). З курсором — наступні записи без повторів.
    3. OFFSET N змушує базу пройти й відкинути N рядків; курсор через WHERE id < :last і індекс одразу переходить до потрібного місця.
    4. Щоб порядок був однозначним при однакових значеннях першого поля; інакше на межах сторінок рядки губляться й повторюються.
    5. Порядок — за id за зростанням, нові новини потрапляють у кінець і не зсувають уже показані сторінки.
    6. Що коментар належить саме цьому посту: умова і за comment_id, і за post_id; інакше — 404.
