    Викладачу¶

    Як вести книгу як курс або інтенсивний воркшоп: скільки часу на крок, що показувати наживо, де студенти застрягають і як перевіряти лаби. Усі команди нижче — з папок steps/NN_* і з тих самих тестів, що й у книзі; нічого додаткового ставити не треба.

    Формати¶

    Формат Тривалість Що входить
    Інтенсив 5 днів × 6 год кроки 1–5 і 8, 10–12; кроки 6, 7, 9 — оглядом; 2–3 лаби; фінальна лаба без захисту
    Курс 14–16 занять × 3 год вступ (Частина I) + по заняттю на крок + 2 заняття на фінальну лабу і захист
    Самостійно з ментором 6–8 тижнів крок на тиждень-два, лаба після кожного другого кроку, щотижневий розбір коду

    Скорочувати можна, не ламаючи послідовності: кожен крок — повний робочий проєкт, тож пропущений крок можна взяти як готовий код і йти далі. Найменше втрат — від пропуску кроку 6 (AI-інструменти) і кроку 7 (LLM): решта кроків від них не залежить, крім полів аналізу в таблиці news (міграція 0002 — уже в коді).

    Тривалість кроків¶

    «Наживо» — пояснення й демонстрація; «практика» — контрольна точка кроку в класі. Лаба — окремо, як домашня робота або окреме заняття.

    Крок Наживо Практика Лаба після кроку Що треба мати в класі
    вступ: Частина I, examples/meteo_api 1.5 год 1 год — лише Python
    0. Що таке API 0.5 год 0.5 год — для тих, хто не писав API
    1. Типи і Pydantic 1.5 год 1 год — mypy
    2. Перший API 2 год 1 год — Postman або newman (за бажанням)
    3. SQLAlchemy і Alembic 2 год 1 год лаба 2 Docker для PostgreSQL (SQLite вистачає для тестів)
    4. Middleware і Redis 2 год 1 год лаба 3 Redis — за бажанням, тести на fakeredis
    5. Тестування API 2 год 1.5 год — —
    6. AI-інструменти 1.5 год 1 год лаба 1 Claude Code — у викладача; студентам вистачить тестів і фікстур
    7. LLM API 2 год 1 год — ключ API — лише для демонстрації, тести на FakeLLM
    8. Безпека 2.5 год 1 год лаба 4 —
    9. Telegram-бот 2 год 1 год лаба 5 токен бота — лише для демонстрації, тести на двійнику Telegram
    10. Docker 1.5 год 1 год лаба 6 Docker у кожного студента
    11. Compose і деплой 2 год 1 год — Docker Compose; сервер — лише у викладача
    12. CI/CD 1.5 год 1 год лаба 7, лаба 8 акаунт GitHub, власний форк
    фінальна лаба 1 год 3–5 год захист Docker для PostgreSQL

    Числа — орієнтир для групи, яка вже пише на Python (функції, класи, pip, git). Для групи без досвіду HTTP додай крок 0 і подвій час на кроки 2–3.

    Як проводити крок¶

    1. Де ми зараз — відкрити попередній крок, pytest -q (кількість тестів — у таблиці маршруту), показати /docs.
    2. Проблема — що не працює або що болить без нового коду. Найкраще — запуск, а не слайд: повільний запит, 500, дубль у базі.
    3. Зміна — git diff --no-index steps/NN-1_… steps/NN_… на екрані, файл за файлом, у тому порядку, як на сторінці кроку.
    4. Результат — тести кроку, запит у /docs або Postman.
    5. Правило — що з цього варто забрати в будь-який проєкт; одне речення на дошці.

    git diff --no-index між сусідніми кроками — головний інструмент викладача: студент бачить, що крок N+1 — це крок N плюс конкретні зміни, а не новий проєкт.

    Що показувати наживо¶

    Те, що студенти мають побачити, а не прочитати. Кожна демонстрація — до 10 хвилин, з підготовленим запасним виводом (вивід є на сторінках кроків).

    Крок Демонстрація Що має запам'ятатися
    1 mypy знаходить помилку в examples/after_typed.py, а Pydantic — у даних типи перевіряють код, Pydantic — дані; потрібні обидва
    2 requests.get в async def — сервер не відповідає навіть на /health блокуючий виклик зупиняє весь цикл подій
    2 /docs будується з анотацій; 422 з detail[].loc параметри — це контракт, порушення видно одразу
    3 alembic revision --autogenerate → прочитати файл → upgrade / downgrade autogenerate — чернетка
    3 два одночасні збори з «перевір, потім встав» → IntegrityError унікальність гарантує база, а не Python
    4 X-Cache: MISS → HIT → запис → знову MISS; redis-cli MONITOR поруч інвалідація через версію, без KEYS
    5 прибрати рядок у коді → червоний тест; mock.patch не там, де шукають тест цінний тим, що падає
    6 агент пише парсер за тестами й фікстурою; CLAUDE.md і дозволи AI працює в рамках тестів, а не замість них
    7 FakeLLM проти справжнього ключа; circuit breaker відкривається після збоїв зовнішній сервіс падає — застосунок ні
    8 запит на http://169.254.169.254/… через safe_fetch → відмова; JWT з чужим підписом → 401 SSRF і підпис — не теорія
    9 бот у Telegram на телефоні проєктора; ті самі сценарії — у тестах на двійнику бот — ще один інтерфейс над тією ж логікою
    10 docker run, HEALTHCHECK → healthy, docker stop — коректна зупинка образ — це артефакт, який перевіряють тестами
    11 docker compose up --wait, міграції до старту API, бекап → відновлення порядок старту — частина системи
    12 PR з падінням у job postgres (alembic check), потім виправлення CI ловить те, що локально «працює»
    фінал EXPLAIN ANALYZE до й після індексу; індекс на «не тому» виразі вимір важливіший за переконання

    Типові питання студентів¶

    Питання Коротка відповідь Де в книзі
    Навіщо дві моделі на одну новину (NewsItem і NewsRow)? одна перевіряє дані на вході, друга — рядок таблиці; їхні причини змінюватися різні крок 3
    Чому /api/news/search повертає 422, а не результат? маршрут з параметром /{news_id} оголошено раніше — конкретні шляхи йдуть першими крок 2, крок 3
    async def чи def? async def — лише з await на неблокуючих викликах; блокуючий код — у def Частина IV
    Чому не можна передати сесію бази у фонову задачу? задача живе довше за запит: сесія вже закрита, COMMIT ніхто не зробить крок 4
    Чому інвалідація кешу в middleware, а не в ендпоінті? COMMIT робить get_db після ендпоінта; інвалідація до COMMIT дає старі дані під новою версією крок 4
    Тести зелені на fakeredis і SQLite — цього досить? для логіки — так; для гонок, ON CONFLICT, планів запитів — прогін на справжніх серверах крок 5, крок 12
    Навіщо FakeLLM, якщо є ключ? тести без мережі, без грошей і з передбачуваною відповіддю крок 7
    JWT можна «розшифрувати» — це дірка? JWT підписаний, а не зашифрований: читати може будь-хто, підробити — лише власник секрету Частина VIII
    Чому бот не ходить в API по HTTP? бот і API — два інтерфейси над тими самими репозиторіями; зайвий мережевий виклик — ще одна точка збою крок 9
    Чому в образі немає pytest? продакшн-контейнеру потрібні лише залежності запуску (requirements.txt) крок 10
    Навіщо alembic check у CI, якщо міграції вже є? ловить модель, змінену без міграції (і навпаки) крок 12
    Я створив індекс, а запит не прискорився індекс має збігатися з виразом, який реально надсилає код; дивись EXPLAIN фінальна лаба

    Як перевіряти лаби¶

    Кожна лаба має критерії приймання — файл тестів на її сторінці. Студент здає папку з копією кроку (або гілку у своєму форку). Перевірка однакова для всіх лаб:

    # 1. що змінено — порівняно з кроком-основою
git diff --no-index --stat steps/NN_<topic> <папка студента>

# 2. старі тести не чіпали (очікувано: лише нові файли або зміни, які лаба прямо вимагає)
git diff --no-index --stat steps/NN_<topic>/tests <папка студента>/tests

# 3. тести приймання — свіжа копія зі сторінки лаби, а не та, що в студента
cp test_<лаба>.py <папка студента>/tests/
cd <папка студента>
pytest -q                       # усі тести кроку + тести приймання
mypy --strict news_hub          # там, де крок його проходить (кроки 1–12)

    Додатково — за типом лаби:

    Лаба Ще що запустити
    міграції, індекси (фінальна) alembic upgrade head && alembic check && alembic downgrade -1 && alembic upgrade head — на SQLite і на PostgreSQL; тести з TEST_DATABASE_URL
    кеш, rate limit тести з TEST_REDIS_URL=redis://localhost:6379/15 — на справжньому Redis
    Docker (лаба 6) pytest -m docker — збирає й запускає образ
    CI (лаба 7) команди job локально + посилання на зелений запуск у форку студента

    Правила, які варто оголосити заздалегідь:

    • Тест приймання береться зі сторінки, а не з папки студента. Студент міг «полагодити» тест замість коду.
    • Лаба без зеленого pytest -q не приймається, навіть якщо тести приймання проходять: зламаний старий тест — це регресія.
    • Розв'язок не мусить збігатися з «Підходом до розв'язку». Будь-який підхід, що проходить тести, зберігає шари (SQL — у репозиторії, правила доступу — у залежностях, а не в кожному ендпоінті) і не дублює код, — приймається.
    • «Що перевірити самому» — питання для усного захисту лаби (5 хвилин): студент показує вивід і пояснює.

    Що можна пропустити¶

    • Крок 0 — для групи, яка вже писала HTTP-клієнти чи сервери.
    • Крок 6 — якщо в класі немає доступу до AI-агента; RSS-джерело кроку 6 можна взяти готовим, а лабу 1 зробити руками.
    • Живий LLM і живий бот (кроки 7 і 9) — демонстрація у викладача; студенти працюють з FakeLLM і двійником Telegram, і всі тести від цього не залежать.
    • Деплой на сервер (крок 11) — показати один раз; студентам достатньо docker compose up --wait локально.
    • Публікація образу в ghcr.io (крок 12) — потребує власного форку; без неї решта CI працює.
