    Задача¶

    Патерн — назва для рішення, яке повторюється: «проблема такого типу розв'язується такою формою коду». Назва не робить код кращим. Вона допомагає у двох речах: швидко пояснити рішення («тут декоратор над клієнтом») і впізнати його в чужому коді.

    Нових патернів на цій сторінці немає. Усі вони вже є в News Hub — з'являлись по одному, у тих кроках, де розв'язували конкретну проблему. Тут ми їх лише називаємо й показуємо, де кожен стоїть.

    Repository¶

    Де: repository.py:31 BaseRepository — get, add, delete, count для будь-якої моделі; :67 NewsRepository, :145 SourceRepository, :156 SubscriptionRepository.

    Навіщо: весь SQL — в одному файлі. Ендпоінт пише await repo.find(lang="uk"), а не select(...). Коли insert_new знадобилось повертати саме нові новини (крок 9, для сповіщень), змінився один метод — а викликачі (API, задача, бот) отримали RETURNING безкоштовно.

    news_hub/repository.py (фрагмент)
    async def insert_new(self, items: Iterable[NewsItem]) -> list[NewNews]:
    """Те саме, але повертає саме нові новини (RETURNING лише вставлених рядків) — для сповіщень."""
    rows = [news_values(item) for item in items]
    if not rows:
        return []
    dialect = self._session.get_bind().dialect.name
    stmt = (postgresql.insert(NewsRow) if dialect == "postgresql" else sqlite.insert(NewsRow)) \
        .values(rows).on_conflict_do_nothing(index_elements=["url"]) \
        .returning(NewsRow.id, NewsRow.title, NewsRow.url)
    return [NewNews(id=row.id, title=row.title, url=row.url) for row in await self._session.execute(stmt)]

    Чим відрізняється від «класичного» Repository: абстрактного інтерфейсу (AbstractNewsRepository) і InMemoryNewsRepository для тестів немає. Тести ходять у справжню базу — SQLite у пам'яті, а в CI ще й PostgreSQL. Це дешевше за другу реалізацію: 363 тести проходять за ~20 с, і перевіряється справжній SQL — ON CONFLICT, lower() з кирилицею, GROUP BY, які фейк у пам'яті не перевірив би. Ціна — тести інтеграційні, а не модульні; де потрібна швидкість без бази, логіка винесена з репозиторію (validate_news, analyze_news).

    Крок: 3, Репозиторій. Методи аналізу — крок 7, SourceRepository — крок 8, SubscriptionRepository і insert_new — крок 9.

    Unit of Work — сесія на запит¶

    Де: db.py:49 get_db; api.py:201 SessionDep = Annotated[AsyncSession, Depends(get_db, scope="function")].

    news_hub/db.py (фрагмент)
    async def get_db() -> AsyncIterator[AsyncSession]:
    """FastAPI Depends: одна сесія (і одна транзакція) на HTTP-запит."""
    async with SessionFactory() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

    Навіщо: AsyncSession SQLAlchemy — це вже Unit of Work: вона збирає зміни й записує їх однією транзакцією. get_db лише проводить межу: одна транзакція = один HTTP-запит. Репозиторій робить flush() (SQL зараз, щоб отримати id і помилки обмежень), але ніколи commit() — COMMIT робить той, хто відкрив сесію. Тому POST /api/scrape (вставка 168 новин + count()) — або все, або нічого.

    Окремого класу UnitOfWork з commit() / rollback() поверх сесії немає — він дублював би AsyncSession.

    Та сама межа в інших входах — і це місце, де найлегше помилитись:

    Вхід Хто відкриває сесію Де COMMIT
    HTTP-запит get_db (db.py:49) після ендпоінта, до відповіді (scope="function")
    фоновий збір run_scrape_job — session_factory() (jobs.py:93) jobs.py:95, один на весь збір
    фоновий аналіз run_analyze_job (jobs.py:120) jobs.py:134 — після кожної новини: збій на 30-й не скасовує 29 оплачених аналізів
    розсилка Notifier (notify.py:88), свій session_factory() notify.py:96 — видалені підписки заблокованих чатів
    update Telegram InjectMiddleware (bot/middlewares.py:48) bot/middlewares.py:55 — після handler

    Крок: 3, Сесія на запит; scope="function" — там само, #scope.

    Cache-aside з версією¶

    Де: cache.py:41 NewsCache; використання — api.py:403 list_news, api.py:443 news_stats; інвалідація — middleware.py:159 invalidate_cache, jobs.py:96, jobs.py:144. Другий кеш — analysis.py:75 AnalysisCache: аналіз за хешем v{PROMPT_VERSION}:{заголовок}, 7 днів.

    Навіщо: читання стрічки — найчастіший запит; база потрібна лише на промаху. Інвалідація — не пошук ключів, а нова версія: INCR news:version після COMMIT. Чому саме після COMMIT і саме в middleware — крок 4. Трасу MISS → HIT → нова версія — Життєвий цикл запиту → кеш; усі ключі — Модель даних → Redis.

    PROMPT_VERSION (analysis.py:30) — та сама ідея для кешу аналізу: змінили промпт чи NewsAnalysis — нова версія в хеші, старі відповіді більше не читаються (test_analysis.py::test_cache_key_depends_on_prompt_version).

    Крок: 4 (стрічка), 7 (аналіз).

    Middleware — ланцюжок обробників¶

    Де: HTTP — api.py:189–192: request_context → SecurityHeadersMiddleware → rate_limit → invalidate_cache. Бот — bot/factory.py:44–45: RateLimitMiddleware (outer) → роутер → InjectMiddleware (inner) → handler.

    Навіщо: правила, що стосуються всіх запитів (журнал, заголовки безпеки, ліміт, кеш), не копіюються в кожен ендпоінт. Кожен обробник або передає запит далі (call_next / handler(event, data)), або відповідає сам — як rate_limit з 429. Шар заголовків безпеки — інший вид middleware: чистий ASGI, який лише загортає send; чому не ще одна функція з call_next — Життєвий цикл → чистий ASGI.

    RateLimiter (middleware.py:105) спільний для обох входів, а ліміти — одна таблиця LIMITS (middleware.py:50): дія → (запитів, секунд). HTTP рахує rate:<дія>:<адреса>; бот — загальний ліміт повідомлень rate:bot:tg<user_id> і, для /scrape, той самий LIMITS["scrape"], що й POST /api/scrape*, з ключем rate:scrape:tg<user_id> (bot/handlers.py:144). Раніше limits був локальною змінною всередині rate_limit, і /scrape у боті мав лише загальний ліміт повідомлень бота — той самий збір rbc.ua через бот можна було запускати частіше, ніж через API (test_bot.py::test_scrape_uses_the_same_rate_limit_as_api).

    Крок: 4, Middleware; бот — 9, Структура бота.

    Ліміт на ціль, а не лише на джерело¶

    Де: security.py:122 LoginGuard, виклик — в admin_token (api.py:619–627).

    Було → стало. Вхід адміна мав один лічильник — rate:login:<адреса>, 5 спроб за 300 с. Він рахує звідки прийшла спроба. Атака на єдиного адміна з тисячі адрес його не помічає: кожна адреса робить свої 5 спроб. LoginGuard рахує на що спрямовані спроби: лише невдалі входи на одне ім'я, з усіх адрес разом.

    rate_limit (middleware) LoginGuard
    ключ rate:login:<адреса> login:fail:<sha256(ім'я.casefold())[:32]>
    що рахує кожну спробу лише невдалу
    ліміт 5 за 300 с (LOGIN_RATE_*) 20 за 900 с (LOGIN_FAIL_*)
    понад ліміт 429 до ендпоінта 429 з Retry-After, bcrypt не запускається
    успішний вхід нічого DEL — лічильник з нуля

    Ціна. Атакувальник може на 15 хвилин закрити вхід і справжньому адміну — це свідомий обмін: для єдиного адміна тимчасова блокада краща за необмежений підбір. Ім'я в ключі — хешем: у Redis не потрапляє довільний рядок від клієнта, а для чужого імені відповідь та сама — ім'я так не вгадаєш.

    Поруч — ще дві зміни того самого ендпоінта: bcrypt (~0,2 с) іде в run_in_threadpool (api.py:624) — інакше кожна спроба входу зупиняла б цикл подій для всіх запитів; відповідь з токеном має Cache-Control: no-store.

    Тест: test_admin_api.py::test_login_lockout_counts_failures_per_name_from_any_address, test_security.py::test_login_guard_counts_per_name_and_resets_on_success.

    Крок: 8.

    Ідемпотентність¶

    Де:

    Що повторюється Чому нічого не ламається Де
    збір тих самих новин INSERT … ON CONFLICT (url) DO NOTHING — у журналі t17: news_found: 168, news_saved: 0 repository.py:81
    підписка на те саме слово ON CONFLICT (chat_id, keyword) DO NOTHING → «Підписка … уже є» repository.py:165
    та сама доставка webhook — і точний повтор, і переслана з новим часом і підписом SET webhook:delivery:<id> <job_id> NX EX 600 → повтор отримує 200 з тим самим завданням, збір не запускається вдруге webhooks.py:79, api.py:778
    повторний аналіз analyzed_at уже є → "source":"db", модель не викликається api.py:562
    update Telegram, надісланий повторно відповідь одразу {"ok": true}, обробка — після, тож Telegram не має причини повторювати api.py:815

    Webhook — найкращий приклад «було → стало». Раніше ключем повтору був підпис, а відповіддю — 409. Але відправник, який не дочекався відповіді, повторює доставку з новим часом — отже, з новим підписом, — і збір запускався вдруге; а точний повтор отримував 409, і відправник вважав доставку невдалою. Тепер відправник надсилає id доставки (X-Webhook-Delivery, як X-GitHub-Delivery), id входить у підпис, а ключ повтору — id. Ідемпотентна відповідь — та сама відповідь, а не помилка: t20 і t21 у запуску повернули job_id з t19. 409 лишився лише для гонки «друга доставка прийшла, поки перша ще не створила завдання» (test_webhooks_api.py::test_resent_delivery_with_new_signature_does_not_scrape_twice, test_webhooks_api.py::test_exact_replay_returns_same_job).

    Liveness і readiness¶

    Де: api.py:369 GET /health — {"status": "ok"} без бази; api.py:374 GET /health/ready — SELECT 1 і PING, інакше 503.

    Навіщо: HEALTHCHECK образу питає /health: якщо PostgreSQL упав, перезапуск API не допоможе — тож контейнер не має ставати «unhealthy». Compose (depends_on: service_healthy) питає /health/ready: nginx має стартувати, коли API справді може відповідати. Назовні — лише "ok" чи назва винятку; адреса бази й текст помилки — у журналі (api.py:377).

    Коли патерн — зайвий¶

    Кожен патерн — ще один рівень, який треба прочитати, щоб зрозуміти код. Він окупається, коли розв'язує наявну проблему. У News Hub кілька «класичних» рішень свідомо не застосовано:

    Чого немає Чому
    абстрактний AbstractNewsRepository + фейк у пам'яті одна реалізація; тести на SQLite в пам'яті швидкі й перевіряють справжній SQL
    окремий клас UnitOfWork AsyncSession уже ним є; межу транзакції проводить get_db
    сервісний шар services/ для кожної дії більшість ендпоінтів — «репозиторій + перевірка»; сценарій виноситься, коли в нього з'являється другий виклик (analyze_news — три входи)
    черга задач (Celery, RQ, arq) задачі короткі, процес один; BackgroundTasks + статус у Redis достатньо — межу описано в Архітектура
    інтерфейс «на майбутнє» з однією реалізацією LLMClient виправданий: провайдерів справді два, а тестам потрібен третій — FakeLLM
