    Модель даних і Redis¶

    News Hub Deep Dive · сторінка 3 з 6. Код: news_hub/tables.py, news_hub/repository.py, migrations/versions/, news_hub/cache.py. Теорія: Частина V. Бази даних, крок 3.

    Задача¶

    Зібрати в одному місці усе, що News Hub зберігає: три таблиці в базі й близько десятка видів ключів у Redis. Для кожного — хто пише, хто читає, скільки живе і з якого кроку з'явилось.

    migrations/env.py бере адресу бази з news_hub.db.DATABASE_URL, а не з alembic.ini: застосунок і міграції завжди дивляться в ту саму базу. Для SQLite вмикається render_as_batch — там немає ALTER COLUMN, і Alembic перебудовує таблицю копіюванням.

    Тести не застосовують міграцій

    Тестова база створюється з Base.metadata.create_all (tests/integration/conftest.py, TestDatabase.create_tables), а не alembic upgrade head. Тож зелений pytest нічого не каже про міграції. Їх перевіряють три інші місця: alembic upgrade head + alembic check у job postgres, тест образу tests/docker/test_image.py::test_migrations_run_on_a_volume і сервіс migrate у smoke-тесті Compose. Як додати міграцію і нічого з цього не пропустити — Як розширювати.

    Індекси і запити, яким вони потрібні¶

    Індекс Стовпці Який запит його використовує
    UNIQUE (url) у news url INSERT … ON CONFLICT (url) DO NOTHING (repository.py:81), 409 у POST /api/news
    ix_news_source, ix_news_lang, ix_news_category по одному фільтри GET /api/news?source=&lang=&category= (repository.py:94) і GROUP BY у /api/news/stats
    ix_news_ai_category, ix_news_sentiment по одному фільтри ?ai_category=&sentiment= і статистика за аналізом
    UNIQUE (url) у sources url 409 у POST /api/sources
    uq_subscription_chat_keyword chat_id, keyword ON CONFLICT (chat_id, keyword) DO NOTHING — повторна підписка нічого не додає (repository.py:165)
    ix_subscriptions_chat_id chat_id for_chat, unsubscribe, remove_chat

    Індексу на title немає: пошук GET /api/news/search — lower(title) LIKE lower('%' || :q || '%') (repository.py:114), а LIKE з % спереду звичайний B-tree однаково не використовує. Для кількох тисяч новин повний перегляд — мілісекунди; для мільйонів знадобився б повнотекстовий пошук PostgreSQL.

    SQLite і PostgreSQL — що відрізняється¶

    Код один, бази дві: SQLite — локально, у тестах і в образі без DATABASE_URL; PostgreSQL — у Compose і в job postgres CI. Різниця сховалась у чотирьох місцях:

    Що Де Чому
    insert(...).on_conflict_do_nothing() repository.py:79–80, :162–163 ON CONFLICT — діалектний синтаксис: postgresql.insert чи sqlite.insert за dialect.name
    lower() з Unicode db.py:32 _unicode_lower вбудований lower() SQLite знає лише латиницю: lower('ЗЕЛЕНСЬК') == 'ЗЕЛЕНСЬК'
    пул з'єднань db.py:26 pool_size=10, max_overflow=20, pool_pre_ping=True — лише для PostgreSQL
    міграції migrations/env.py render_as_batch лише для SQLite

    Ще одна різниця видна у відповіді API. DateTime(timezone=True) у PostgreSQL — timestamp with time zone, а SQLite пояса не зберігає. У запуску на SQLite свіжий аналіз повернув "analyzed_at":"2026-11-12T05:01:56.513569Z" (значення з Python), а той самий аналіз, прочитаний з бази наступним запитом, — "2026-11-12T05:01:56.513569", без Z; scraped_at з SQLite теж без пояса. Клієнт, який порівнює час, має це враховувати — або працювати з PostgreSQL, як у Compose.

    Redis: що там лежить¶

    Redis у News Hub — не одна функція, а шість: кеш стрічки, кеш аналізу, лічильники лімітів, статус задач, стан breaker і пам'ять про доставки webhook. Ось що лежало в ньому після запуску t00–t22 (redis-cli --scan, TTL — у секундах на момент перегляду):

    cb:llm:*, rate:bot:* і rate:scrape:tg* у запуску не з'явились: збоїв провайдера не було, бот не працював. Ім'я в ключі — хешем (sha256("admin")[:32] = 8c6976e5b5410415bde908bd4dee15df): у Redis не потрапляє довільний рядок від клієнта.

    Раніше ключем повтору webhook був сам підпис (webhook:seen:sha256=…, значення 1, повтор → 409). Новий підпис на той самий запит — і повтор проходив; новий ключ тримає id доставки і job_id, тому повтор отримує відповідь першої доставки (Життєвий цикл → повтор webhook).

    Версія кешу: від 0 до 7¶

    Кеш стрічки не видаляється за шаблоном (KEYS news:* блокує Redis) — кожен запис просто збільшує news:version, і старі ключі перестають читатися. У запуску версія дійшла до 7, і кожне збільшення має автора:

    Запит Хто збільшив Чому
    t03 POST /api/scrape middleware invalidate_cache path == "/api/scrape", статус 200
    t06 PATCH /api/news/1 middleware path.startswith("/api/news")
    t11 POST /api/news/2/analyze middleware те саме
    t12 те саме, "source":"db" middleware шлях і статус ті самі — хоча дані не змінились
    t13 POST /api/scrape/jobs run_scrape_job (jobs.py:96) middleware цей шлях не чіпає — фонова задача збільшує сама, після свого COMMIT
    t17 POST /api/scrape middleware —
    t19 POST /api/webhooks/scrape run_scrape_job те саме, що t13

    401 (t15, t16, t22), 409 (t10) і 429 (t18) версію не змінили: invalidate_cache дивиться на status_code < 400. Повтори webhook t20 і t21 (200) — теж: шлях /api/webhooks/scrape middleware не чіпає, а другого збору, який збільшив би версію сам, не було. Рядок t12 — дрібна неефективність: повторний analyze, який віддав збережений результат, теж скидає кеш, бо middleware не знає, чи щось змінилось.

    Якщо Redis недоступний¶

    Не всі частини реагують однаково — і це видно з коду:

    Хто Redis упав Де
    /health/ready 503, "redis": "<назва винятку>" api.py:385
    AnalysisCache промах кешу; аналіз працює, лише дорожче analysis.py:86, :96 — except RedisError
    CircuitBreaker вважає себе закритим, LLM викликається llm.py:244
    NewsCache, RateLimiter, JobStore, LoginGuard, claim_delivery виняток не перехоплюється → 500 cache.py, middleware.py, jobs.py, security.py, webhooks.py

    Тобто кеш аналізу й breaker — «прискорення, а не умова роботи», а кеш стрічки й ліміти без Redis не працюють. У Compose api стартує лише після redis: service_healthy; якщо Redis зникне вже під час роботи, healthcheck api (той самий /health/ready) за кілька перевірок покаже unhealthy у docker compose ps.
