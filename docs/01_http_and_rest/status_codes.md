# Коди відповідей

## Проблема { #problem }

Код відповіді — перше, що бачить клієнт, і часто єдине, на що він дивиться. Мобільний застосунок повторює запит лише на `503`, проксі кешує лише `200`, браузер показує форму входу на `401`. Якщо API повертає `200` з `{"error": ...}` у тілі або `500` на помилку клієнта, кожен клієнт мусить розбирати тіло і вгадувати. Тут потрібно вирішити дві речі: які коди потрібні REST API і які з них FastAPI вже ставить сам.

## Ментальна модель { #mental-model }

Перша цифра — **хто винен і що робити**:

| Клас | Значення | Що робить клієнт |
|---|---|---|
| `2xx` | вийшло | читає тіло (якщо є) |
| `3xx` | шукай деінде | іде за `Location` |
| `4xx` | помилка **клієнта** | виправляє запит; повторювати без змін марно |
| `5xx` | помилка **сервера** | запит може бути правильним; повторити пізніше |

Коди, яких досить для більшості API (RFC 9110, §15):

| Код | Коли | Обов'язкове чи бажане в відповіді |
|---|---|---|
| `200 OK` | успіх з тілом | — |
| `201 Created` | створено новий ресурс | `Location` — адреса ресурсу |
| `202 Accepted` | прийнято, виконується у фоні | адреса, де дізнатися статус |
| `204 No Content` | успіх без тіла (`DELETE`) | тіла немає |
| `400 Bad Request` | запит неможливо обробити з вини клієнта, і точнішого коду немає | опис у `detail` |
| `401 Unauthorized` | клієнт **не автентифікований**: немає облікових даних або вони недійсні | `WWW-Authenticate` — як автентифікуватись |
| `403 Forbidden` | клієнта впізнали, але **прав немає** | — |
| `404 Not Found` | ресурсу немає (або його існування приховують) | — |
| `405 Method Not Allowed` | шлях є, методу немає | `Allow` — дозволені методи |
| `409 Conflict` | конфлікт зі станом ресурсу: дублікат унікального поля, застаріла версія | — |
| `422 Unprocessable Content` | формат правильний, але дані не проходять перевірку | список помилок |
| `429 Too Many Requests` | перевищено ліміт частоти | `Retry-After` — через скільки секунд |
| `500 Internal Server Error` | неочікувана помилка сервера | без подробиць |
| `502 Bad Gateway` | сервер отримав погану відповідь від того, до кого ходив сам | — |
| `503 Service Unavailable` | тимчасово недоступний: перевантаження, залежність лежить | `Retry-After` |

## `400` чи `422` { #400-vs-422 }

RFC 9110 визначає обидва коди:

- **`400`** — загальна помилка клієнта: запит неможливо обробити, і точнішого коду немає.
- **`422 Unprocessable Content`** (раніше — «Unprocessable Entity» з WebDAV, RFC 4918) — тип вмісту зрозумілий, синтаксис правильний, але інструкції в ньому неможливо виконати.

**FastAPI вирішує за тебе: усе, що не пройшло перевірку параметрів і тіла, — `422`.** Навіть синтаксично битий JSON, хоча за буквою RFC це ближче до `400`. Перевірено на [`codes_app.py`](https://github.com/NikoriakViktor/news_hub/blob/main/examples/http_anatomy/codes_app.py):

```text
--- битий JSON  {"slug": "abc"
HTTP/1.1 422 Unprocessable Entity
{"detail":[{"type":"json_invalid","loc":["body",14],"msg":"JSON decode error","input":{},"ctx":{"error":"Expecting ',' delimiter"}}]}

--- JSON, надісланий як text/plain
HTTP/1.1 422 Unprocessable Entity
{"detail":[{"type":"model_attributes_type","loc":["body"],"msg":"Input should be a valid dictionary or object to extract fields from","input":"{\"slug\": \"abc\"}"}]}

--- без тіла
HTTP/1.1 422 Unprocessable Entity
{"detail":[{"type":"missing","loc":["body"],"msg":"Field required","input":null}]}
```

Практичне правило для FastAPI:

| Ситуація | Код | Хто ставить |
|---|---|---|
| тип, формат, обмеження `Field`, відсутнє поле, битий JSON | `422` | FastAPI сам |
| дані коректні за схемою, але порушують правило, якого схемою не описати: адреса веде в приватну мережу, тіло — не той тип події | `400` | ти: `HTTPException(400, ...)` |
| конфлікт з тим, що вже є в базі | `409` | ти |

Головне — однаковість: один і той самий вид помилки завжди з тим самим кодом і в тому самому форматі. Хто хоче `400` замість `422` для всього API, підміняє обробник `RequestValidationError` (`@app.exception_handler(RequestValidationError)`).

Константа в коді: `status.HTTP_422_UNPROCESSABLE_CONTENT`. Стара назва `HTTP_422_UNPROCESSABLE_ENTITY` у Starlette застаріла й дає попередження:

```text
'HTTP_422_UNPROCESSABLE_ENTITY' is deprecated. Use 'HTTP_422_UNPROCESSABLE_CONTENT' instead.
```

## Що FastAPI відповідає сам { #automatic }

```text
--- необроблений виняток (1 / 0)
HTTP/1.1 500 Internal Server Error
content-type: text/plain; charset=utf-8
Internal Server Error

--- status_code=204, а функція повернула {"deleted": 1}
HTTP/1.1 204 No Content

--- HTTPBearer, заголовка Authorization немає
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer
{"detail":"Not authenticated"}
```

- **`500`** — клієнт бачить лише «Internal Server Error», трасування стеку — тільки в журналі сервера. Так і має бути: подробиці помилки підказують атакувальнику, що всередині.
- **`204`** — тіло, яке повернула функція, FastAPI відкидає: відповідь `204` за стандартом без тіла.
- **`401` з `WWW-Authenticate: Bearer`** — `HTTPBearer` у FastAPI 0.162 відповідає саме так. Старі версії FastAPI повертали тут `403`, тож у старих підручниках і проєктах можна зустріти `403` на відсутній токен.

## У News Hub { #news-hub }

| Код | Де | Крок |
|---|---|---|
| `201` | `POST /api/news` | [3](../tutorials/03_sqlalchemy_alembic/index.md) |
| `202` | `POST /api/scrape/jobs` → `job_id`, статус — `GET /api/scrape/jobs/{job_id}` | [4](../tutorials/04_middleware_redis/index.md) |
| `204` | `DELETE /api/news/{id}` | 3 |
| `400` | RSS-джерело з адресою в приватній мережі (SSRF); webhook Telegram, у якому не update | [8](../tutorials/08_security/index.md), [9](../tutorials/09_telegram_bot/index.md) |
| `401` + `WWW-Authenticate: Bearer` | немає або недійсний JWT; неправильний пароль адміна | 8 |
| `403` | токен дійсний, але не адмін | 8 |
| `409` | новина з таким `url` уже є | 3 |
| `422` | усе, що не пройшло перевірку моделей | 2 |
| `429` + `Retry-After` | rate limit збору, аналізу LLM і входу адміна | 4, 7, 8 |
| `502` | провайдер LLM відповів помилкою | [7](../tutorials/07_llm_api/index.md) |
| `503` + `Retry-After` | circuit breaker відкритий або немає ключа LLM; `/health/ready`, коли база чи Redis недоступні | 7, [10](../tutorials/10_docker/index.md) |

`409` у News Hub ставить не перевірка «а чи є вже така новина» перед вставкою, а сама база: унікальний індекс на `url` і перехоплений `IntegrityError`. Перевірка перед вставкою не рятує від двох одночасних запитів: обидва побачать «немає» і обидва вставлять.

## Типові помилки { #mistakes }

| Помилка | Наслідок | Як правильно |
|---|---|---|
| `200` з `{"error": "..."}` | клієнти, кеші й моніторинг вважають запит успішним | код помилки `4xx`/`5xx` |
| дублікат → необроблений `IntegrityError` | клієнт отримує `500`, хоча винен він | унікальний індекс + `except IntegrityError` → `409` |
| «перевірити, потім вставити» замість унікального індексу | при двох одночасних запитах — дублікат | обмеження в базі; перевірка — лише для гарного повідомлення |
| `401` і `403` навпаки | клієнт з простроченим токеном не знає, що треба увійти знову | немає/недійсні облікові дані — `401`, немає прав — `403` |
| `401` без `WWW-Authenticate` | порушення RFC 9110; клієнти не знають схеми | `HTTPException(401, ..., headers={"WWW-Authenticate": "Bearer"})` |
| `429`/`503` без `Retry-After` | клієнти повторюють одразу й поглиблюють перевантаження | `Retry-After: <секунди>` |
| `404` на неіснуючий, `403` на чужий ресурс | атакувальник перебором дізнається, які id існують | для чужого — теж `404` |
| `HTTP_422_UNPROCESSABLE_ENTITY` у новому коді | попередження про застарілість | `HTTP_422_UNPROCESSABLE_CONTENT` |

## Налагодження { #debugging }

- `422` — читай `detail[].type` і `loc`: `json_invalid` — битий JSON, `missing` — немає поля, `model_attributes_type` — тіло не об'єкт (часто чужий `Content-Type`).
- `500` — причина лише в журналі сервера; у відповіді її немає навмисно.
- Код, який очікуєш, і код, який приходить, різняться — перевір `status_code=` у декораторі й `HTTPException`, а також middleware, яке може відповісти раніше (`429`).

## Безпека { #security }

- **Без подробиць у `5xx`.** Трасування, SQL, назви таблиць — у журнал, не клієнту. FastAPI так поводиться за замовчуванням; власний обробник винятків не повинен це ламати.
- **`404` замість `403` для чужих ресурсів**, якщо сам факт існування — інформація (id замовлень, користувачів).
- **Однакова відповідь на «немає користувача» і «неправильний пароль»** — `401` з тим самим текстом, інакше вхід підказує, які логіни існують. У News Hub — «неправильне ім'я або пароль».
- **`429` — частина захисту**, а не ввічливість: без ліміту вхід перебирають паролі, а дорогі ендпоінти (LLM) спалюють квоту.

## Питання { #questions }

1. Чим `4xx` відрізняється від `5xx` для клієнта, який вирішує, чи повторювати запит?
2. Що поверне FastAPI на синтаксично битий JSON? Чи збігається це з буквою RFC?
3. Коли в FastAPI-проєкті доречний `400`, якщо всю перевірку схеми робить `422`?
4. Користувач надіслав запит без токена. `401` чи `403`? А з дійсним токеном без прав?
5. Чому перевірка «новини з таким `url` ще немає» перед вставкою не замінює унікальний індекс?
6. Що мають містити відповіді `429` і `503`?

??? success "Відповіді"

    1. `4xx` — запит неправильний, повтор без змін марний; `5xx` — винен сервер, можна повторити пізніше.
    2. `422` з `type: json_invalid`. За RFC синтаксична помилка — радше `400`; FastAPI свідомо відповідає `422` на будь-яку помилку перевірки.
    3. Для правил, яких схемою не описати: адреса RSS-джерела веде в приватну мережу, тіло webhook — не той тип події.
    4. Без токена — `401` з `WWW-Authenticate`; з дійсним токеном без прав — `403`.
    5. Два одночасні запити обидва побачать «немає» й обидва вставлять. Унікальний індекс у базі відхилить другий — і його `IntegrityError` стає `409`.
    6. Заголовок `Retry-After` — через скільки секунд повторити.
