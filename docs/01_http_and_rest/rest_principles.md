# Принципи REST

## Проблема { #problem }

«REST API» сьогодні кажуть майже про будь-який JSON поверх HTTP. Але REST — конкретний архітектурний стиль з дисертації Роя Філдінга (2000) з шістьма обмеженнями. Частину з них сучасні JSON API виконують суворо, бо без цього вони ламаються під навантаженням. Іншу частину майже всі свідомо пропускають. Щоб проєктувати API, а не копіювати чужі адреси, треба знати, що з цього що.

## Ментальна модель { #mental-model }

| Обмеження Філдінга | Що означає | У JSON API на практиці |
|---|---|---|
| клієнт — сервер | інтерфейс і дані розділені, розвиваються окремо | **так**: фронтенд, мобільний застосунок, бот — окремі клієнти одного API |
| відсутність стану (stateless) | кожен запит несе все, що потрібно для його обробки; сервер не пам'ятає «розмову» | **так**, і це вимога масштабування: токен у кожному запиті, дані — у базі, а не в пам'яті процесу |
| кешованість | відповідь позначає, чи можна її кешувати | **частково**: `Cache-Control` і `ETag` ставлять для публічних даних, решту часто не кешують зовсім |
| однорідний інтерфейс | ресурси з адресами, дії — стандартними методами, повідомлення самоописні | **так** для ресурсів і методів; **ні** для гіпермедіа (HATEOAS) |
| багаторівнева система | між клієнтом і сервером можуть бути проксі, балансувальник, CDN | **так**: nginx перед API, CDN перед статикою |
| код на вимогу (необов'язкове) | сервер може віддати клієнту код для виконання | **ні** для JSON API (це світ браузерів і JavaScript) |

Однорідний інтерфейс складається з чотирьох частин, і саме тут різниця між «REST» і «RESTful JSON API» найбільша:

| Частина | Застосовують? |
|---|---|
| ідентифікація ресурсів: `/api/news/42` | так |
| дії через представлення: клієнт надсилає JSON, сервер змінює ресурс | так |
| самоописні повідомлення: метод, код, `Content-Type` кажуть, що відбувається | так — [методи](http_methods.md), [коди](status_codes.md) |
| гіпермедіа як двигун стану (HATEOAS): клієнт дізнається про наступні дії з посилань у відповіді | майже ніколи |

## Відсутність стану: що буває без неї { #stateless }

[Крок 2](../tutorials/02_fastapi_basics/index.md) News Hub тримає новини в пам'яті процесу (`NewsStore` в `app.state`). Для одного процесу uvicorn це працює. Ось що буває з двома:

```bash
uvicorn news_hub.api:app --port 8017 --workers 2
curl -X POST localhost:8017/api/scrape -H 'content-type: application/json' -d '{"source":"snapshot"}'
for i in 1 2 3 4 5 6 7 8; do curl -s localhost:8017/api/news/count; echo -n " "; done
```

```text
{"source":"snapshot","mode":"async","total_time":0.0,"pages":[],"news_found":168,"news_valid":168,"news_saved":168,...}
{"count":0} {"count":0} {"count":168} {"count":168} {"count":168} {"count":168} {"count":0} {"count":168}
```

Збір потрапив в один воркер, і лише той воркер «знає» про 168 новин. Кожен наступний запит дістається довільному воркеру, тож клієнт бачить то `0`, то `168`. Те саме буде з кількома контейнерами за балансувальником.

Тому з [кроку 3](../tutorials/03_sqlalchemy_alembic/index.md) новини в базі, з [кроку 4](../tutorials/04_middleware_redis/index.md) кеш і лічильники rate limit — у Redis, а з [кроку 8](../tutorials/08_security/index.md) адмін ідентифікує себе JWT у кожному запиті, а не сесією в пам'яті сервера. «Stateless» не означає «без даних». Стан є, але він живе у спільному сховищі, а не в процесі, який обробив попередній запит.

## Кешованість: HTTP-кеш і серверний кеш { #caching }

Це дві різні речі:

| | HTTP-кеш (REST) | Серверний кеш (News Hub, крок 4) |
|---|---|---|
| де живе | у браузері, проксі, CDN | у Redis поруч з API |
| хто вирішує | клієнт за заголовками `Cache-Control`, `ETag` | код сервера |
| що економить | запит не доходить до сервера взагалі, або тіло не передається | сервер не ходить у базу |
| FastAPI робить сам | ні | ні |

HTTP-кеш — [`examples/http_anatomy/cache_app.py`](https://github.com/NikoriakViktor/news_hub/blob/main/examples/http_anatomy/cache_app.py). `ETag` — «відбиток» поточної версії ресурсу. Клієнт надсилає його назад в `If-None-Match`, і якщо версія та сама, сервер відповідає `304` без тіла:

```python title="cache_app.py (фрагмент)"
etag = '"' + hashlib.sha256(body).hexdigest()[:16] + '"'
headers = {"ETag": etag, "Cache-Control": "public, max-age=60"}
if if_none_match == etag:
    return Response(status_code=304, headers=headers)
```

```text
1 → 200 "071baf8dc9520afd" public, max-age=60 47 байтів
2 → 304 "071baf8dc9520afd" 0 байтів
3 → 200 "f5cf06a5b2962262" {'slug': 'rest', 'title': 'Принципи REST (оновлено)'}
/me → private, no-store
```

1. Перший запит — повне тіло, `ETag` і дозвіл кешувати 60 секунд.
2. Повтор з тим самим `ETag` — `304`, 0 байтів тіла: клієнт бере збережену копію.
3. Після зміни статті `ETag` інший — знову `200` з новим тілом.
4. Особисті дані — `private, no-store`: їх не можна класти в спільний кеш.

У News Hub HTTP-кешу немає: стрічка новин змінюється з кожним збором, а серверний кеш у Redis з інвалідацією після запису ([крок 4](../tutorials/04_middleware_redis/index.md)) дає більше контролю.

## HATEOAS: чому його пропускають { #hateoas }

За Філдінгом клієнт не повинен знати адреси заздалегідь: він починає з кореня API і йде за посиланнями з відповідей, як людина на сайті. На практиці клієнти JSON API пишуть люди, які читають документацію, і генерують з **OpenAPI** ([Частина III](../03_fastapi_core/openapi.md)). Контракт фіксує схема, а не посилання в кожній відповіді. Окремі стандарти формату (JSON:API, HAL) з обов'язковими `links` прижились мало.

Мінімум гіпермедіа, який варто лишити:

- `201 Created` + заголовок `Location` — де живе створений ресурс ([методи HTTP](http_methods.md#in-practice));
- `202 Accepted` + адреса статусу — у News Hub `POST /api/scrape/jobs` повертає `job_id`, а статус — за `GET /api/scrape/jobs/{job_id}` ([крок 4](../tutorials/04_middleware_redis/index.md));
- `next`/`prev` у пагінації, якщо вона курсорна.

## Ресурси й адреси { #resources }

Ресурс — іменник, дія — метод ([методи HTTP](http_methods.md#design)). Решта — домовленості, які варто тримати однаковими в межах API:

| Питання | Поширений вибір | У News Hub |
|---|---|---|
| множина чи однина | множина для колекцій: `/items`, `/items/{id}` | `/api/news`, `/api/news/{id}` |
| коса риска в кінці | без неї; головне — однаково скрізь | без неї |
| дія, що не CRUD | `POST` на підресурс-дієслово | `POST /api/scrape`, `POST /api/news/{id}/analyze` |
| вкладеність | не глибше одного рівня | `/api/news/{id}/analyze` |

Коса риска важить більше, ніж здається: маршрут `/articles/` на запит `/articles` дає `307` з редиректом ([HTTP-запит і відповідь](http_anatomy.md#not-reached)), а не дані й не `405`.

## Типові помилки { #mistakes }

| Помилка | Наслідок | Як правильно |
|---|---|---|
| стан у пам'яті процесу (словник, глобальна змінна, сесія) | з кількома воркерами чи контейнерами — різні відповіді на той самий запит | база, Redis, токен у запиті |
| `Cache-Control: public` на персональних даних | CDN або корпоративний проксі віддасть чужі дані іншим | `private, no-store` для всього, що залежить від користувача |
| вважати Redis-кеш «кешуванням з REST» | клієнти й проксі не знають, що можна кешувати | HTTP-кеш — через заголовки, серверний — окремо |
| дієслова в адресах замість методів: `/getNews`, `/deleteNews?id=1` | обходить семантику методів, ламає кеші й безпеку `GET` | `GET /api/news`, `DELETE /api/news/1` |
| однакова модель для створення й відповіді | клієнт може задати `id` чи службові поля | окремі `Create` і `Out` моделі ([методи HTTP](http_methods.md#security)) |

## Безпека { #security }

- **Кеш — канал витоку.** Будь-яка відповідь з даними користувача — `Cache-Control: private` або `no-store`. Помилка тут роздає чужі дані всім, хто йде через той самий проксі.
- **Відсутність стану на сервері — плюс для безпеки сесій**: немає таблиці сесій, яку можна вкрасти чи переповнити. Але токен у кожному запиті має бути коротким за часом життя і передаватися лише через HTTPS ([Частина VIII](../08_security/README.md)).
- **Багаторівнева система означає, що IP клієнта бачить лише перший рівень.** API за nginx отримує адресу nginx, а справжню — з `X-Forwarded-For`, якому можна вірити лише від свого проксі ([крок 11](../tutorials/11_compose_deploy/index.md)).

## Питання { #questions }

1. Які обмеження REST сучасні JSON API виконують, а які ні?
2. Чому News Hub кроку 2 з `--workers 2` показує то `0`, то `168` новин?
3. Чим HTTP-кеш відрізняється від кешу стрічки в Redis?
4. Що поверне сервер на запит з `If-None-Match`, що збігається з поточним `ETag`, і скільки байтів тіла?
5. Що замінило HATEOAS у більшості JSON API? Який мінімум гіпермедіа варто лишити?

??? success "Відповіді"

    1. Виконують: клієнт — сервер, відсутність стану, ресурси й методи, багаторівневу систему; кешування — частково. Пропускають: HATEOAS і код на вимогу.
    2. Кожен воркер — окремий процес зі своїм `NewsStore`; збір потрапив лише в один.
    3. HTTP-кеш живе в клієнті чи проксі й керується заголовками відповіді; кеш у Redis — на сервері, ним керує код.
    4. `304 Not Modified`, 0 байтів тіла.
    5. Документація й схема OpenAPI. Мінімум: `Location` після `201`, адреса статусу після `202`, посилання пагінації.
