# Викладачу { #teaching-guide }

Як вести книгу як курс або інтенсивний воркшоп: скільки часу на крок, що показувати наживо, де студенти
застрягають і як перевіряти [лаби](labs/README.md). Усі команди нижче — з папок `steps/NN_*` і з тих самих тестів, що й у
книзі; нічого додаткового ставити не треба.

## Формати { #formats }

| Формат | Тривалість | Що входить |
|---|---|---|
| **Інтенсив** | 5 днів × 6 год | кроки 1–5 і 8, 10–12; кроки 6, 7, 9 — оглядом; 2–3 лаби; фінальна лаба без захисту |
| **Курс** | 14–16 занять × 3 год | вступ (Частина I) + по заняттю на крок + 2 заняття на фінальну лабу і захист |
| **Самостійно з ментором** | 6–8 тижнів | крок на тиждень-два, лаба після кожного другого кроку, щотижневий розбір коду |

Скорочувати можна, не ламаючи послідовності: кожен крок — повний робочий проєкт, тож пропущений крок можна взяти як
готовий код і йти далі. Найменше втрат — від пропуску кроку 6 (AI-інструменти) і кроку 7 (LLM): решта кроків від них не
залежить, крім полів аналізу в таблиці `news` (міграція 0002 — уже в коді).

## Як проводити крок { #step-routine }

1. **Де ми зараз** — відкрити попередній крок, `pytest -q` (кількість тестів — у
   [таблиці маршруту](tutorials/README.md)), показати `/docs`.
2. **Проблема** — що не працює або що болить без нового коду. Найкраще — запуск, а не слайд: повільний запит,
   `500`, дубль у базі.
3. **Зміна** — `git diff --no-index steps/NN-1_… steps/NN_…` на екрані, файл за файлом, у тому порядку, як на сторінці кроку.
4. **Результат** — тести кроку, запит у `/docs` або Postman.
5. **Правило** — що з цього варто забрати в будь-який проєкт; одне речення на дошці.

`git diff --no-index` між сусідніми кроками — головний інструмент викладача: студент бачить, що крок N+1 — це крок N
плюс конкретні зміни, а не новий проєкт.

## Що показувати наживо { #live-demo }

Те, що студенти мають **побачити**, а не прочитати. Кожна демонстрація — до 10 хвилин, з підготовленим запасним
виводом (вивід є на сторінках кроків).

| Крок | Демонстрація | Що має запам'ятатися |
|---|---|---|
| 1 | `mypy` знаходить помилку в `examples/after_typed.py`, а Pydantic — у даних | типи перевіряють код, Pydantic — дані; потрібні обидва |
| 2 | `requests.get` в `async def` — сервер не відповідає навіть на `/health` | блокуючий виклик зупиняє весь цикл подій |
| 2 | `/docs` будується з анотацій; `422` з `detail[].loc` | параметри — це контракт, порушення видно одразу |
| 3 | `alembic revision --autogenerate` → **прочитати** файл → `upgrade` / `downgrade` | autogenerate — чернетка |
| 3 | два одночасні збори з «перевір, потім встав» → `IntegrityError` | унікальність гарантує база, а не Python |
| 4 | `X-Cache: MISS` → `HIT` → запис → знову `MISS`; `redis-cli MONITOR` поруч | інвалідація через версію, без `KEYS` |
| 5 | прибрати рядок у коді → червоний тест; `mock.patch` не там, де шукають | тест цінний тим, що падає |
| 6 | агент пише парсер за тестами й фікстурою; `CLAUDE.md` і дозволи | AI працює в рамках тестів, а не замість них |
| 7 | `FakeLLM` проти справжнього ключа; circuit breaker відкривається після збоїв | зовнішній сервіс падає — застосунок ні |
| 8 | запит на `http://169.254.169.254/…` через `safe_fetch` → відмова; JWT з чужим підписом → `401` | SSRF і підпис — не теорія |
| 9 | бот у Telegram на телефоні проєктора; ті самі сценарії — у тестах на двійнику | бот — ще один інтерфейс над тією ж логікою |
| 10 | `docker run`, `HEALTHCHECK` → `healthy`, `docker stop` — коректна зупинка | образ — це артефакт, який перевіряють тестами |
| 11 | `docker compose up --wait`, міграції до старту API, бекап → відновлення | порядок старту — частина системи |
| 12 | PR з падінням у job `postgres` (`alembic check`), потім виправлення | CI ловить те, що локально «працює» |
| фінал | `EXPLAIN ANALYZE` до й після індексу; індекс на «не тому» виразі | вимір важливіший за переконання |

## Типові питання студентів { #faq }

| Питання | Коротка відповідь | Де в книзі |
|---|---|---|
| Навіщо дві моделі на одну новину (`NewsItem` і `NewsRow`)? | одна перевіряє дані на вході, друга — рядок таблиці; їхні причини змінюватися різні | [крок 3](tutorials/03_sqlalchemy_alembic/index.md) |
| Чому `/api/news/search` повертає `422`, а не результат? | маршрут з параметром `/{news_id}` оголошено раніше — конкретні шляхи йдуть першими | [крок 2](tutorials/02_fastapi_basics/checkpoint.md), [крок 3](tutorials/03_sqlalchemy_alembic/checkpoint.md) |
| `async def` чи `def`? | `async def` — лише з `await` на неблокуючих викликах; блокуючий код — у `def` | [Частина IV](04_async/README.md) |
| Чому не можна передати сесію бази у фонову задачу? | задача живе довше за запит: сесія вже закрита, COMMIT ніхто не зробить | [крок 4](tutorials/04_middleware_redis/index.md) |
| Чому інвалідація кешу в middleware, а не в ендпоінті? | COMMIT робить `get_db` після ендпоінта; інвалідація до COMMIT дає старі дані під новою версією | [крок 4](tutorials/04_middleware_redis/index.md) |
| Тести зелені на fakeredis і SQLite — цього досить? | для логіки — так; для гонок, `ON CONFLICT`, планів запитів — прогін на справжніх серверах | [крок 5](tutorials/05_api_testing/index.md), [крок 12](tutorials/12_ci_cd/what_to_check.md) |
| Навіщо `FakeLLM`, якщо є ключ? | тести без мережі, без грошей і з передбачуваною відповіддю | [крок 7](tutorials/07_llm_api/index.md) |
| JWT можна «розшифрувати» — це дірка? | JWT підписаний, а не зашифрований: читати може будь-хто, підробити — лише власник секрету | [Частина VIII](08_security/README.md) |
| Чому бот не ходить в API по HTTP? | бот і API — два інтерфейси над тими самими репозиторіями; зайвий мережевий виклик — ще одна точка збою | [крок 9](tutorials/09_telegram_bot/index.md) |
| Чому в образі немає `pytest`? | продакшн-контейнеру потрібні лише залежності запуску (`requirements.txt`) | [крок 10](tutorials/10_docker/index.md) |
| Навіщо `alembic check` у CI, якщо міграції вже є? | ловить модель, змінену без міграції (і навпаки) | [крок 12](tutorials/12_ci_cd/what_to_check.md#alembic-check) |
| Я створив індекс, а запит не прискорився | індекс має збігатися з виразом, який реально надсилає код; дивись `EXPLAIN` | [фінальна лаба](labs/final_search_index.md#measure) |

## Як перевіряти лаби { #grading-labs }

Кожна лаба має **критерії приймання** — файл тестів на її сторінці. Студент здає папку з копією кроку (або гілку у
своєму форку). Перевірка однакова для всіх лаб:

```bash
# 1. що змінено — порівняно з кроком-основою
git diff --no-index --stat steps/NN_<topic> <папка студента>

# 2. старі тести не чіпали (очікувано: лише нові файли або зміни, які лаба прямо вимагає)
git diff --no-index --stat steps/NN_<topic>/tests <папка студента>/tests

# 3. тести приймання — свіжа копія зі сторінки лаби, а не та, що в студента
cp test_<лаба>.py <папка студента>/tests/
cd <папка студента>
pytest -q                       # усі тести кроку + тести приймання
mypy --strict news_hub          # там, де крок його проходить (кроки 1–12)
```

Додатково — за типом лаби:

| Лаба | Ще що запустити |
|---|---|
| міграції, індекси (фінальна) | `alembic upgrade head && alembic check && alembic downgrade -1 && alembic upgrade head` — на SQLite і на PostgreSQL; тести з `TEST_DATABASE_URL` |
| кеш, rate limit | тести з `TEST_REDIS_URL=redis://localhost:6379/15` — на справжньому Redis |
| Docker (лаба 6) | `pytest -m docker` — збирає й запускає образ |
| CI (лаба 7) | команди job локально + посилання на зелений запуск у форку студента |

Правила, які варто оголосити заздалегідь:

- **Тест приймання береться зі сторінки, а не з папки студента.** Студент міг «полагодити» тест замість коду.
- **Лаба без зеленого `pytest -q` не приймається**, навіть якщо тести приймання проходять: зламаний старий тест —
  це регресія.
- **Розв'язок не мусить збігатися з «Підходом до розв'язку».** Будь-який підхід, що проходить тести, зберігає шари
  (SQL — у репозиторії, правила доступу — у залежностях, а не в кожному ендпоінті) і не дублює код, — приймається.
- **«Що перевірити самому»** — питання для усного захисту лаби (5 хвилин): студент показує вивід і пояснює.

## Оцінювання { #grading }

### Лаба { #grading-lab }

| Критерій | Балів | Максимум — це |
|---|---:|---|
| тести приймання | 40 | усі зелені на свіжій копії тестів |
| регресії і типи | 20 | `pytest -q` зелений, `mypy --strict` чистий, старі тести не змінені без потреби |
| якість рішення | 20 | шари збережено, немає дублювання, імена й повідомлення помилок зрозумілі |
| захист | 20 | відповіді на «Що перевірити самому» з реальним виводом |

### Фінальна лаба і проєкт { #grading-final }

Технічна частина — як у лаби (вище), з обов'язковим `EXPLAIN ANALYZE` до й після індексу на даних студента.
Захист — за [чеклістом](labs/final_search_index.md#defense):

| Критерій | Балів | Максимум — це |
|---|---:|---|
| проблема | 20 | конкретна людина й ситуація; хоча б один факт з розмови чи джерела |
| рішення і демо | 25 | один сценарій наживо без збоїв; зрозуміло без пояснень |
| технічна глибина | 25 | одна діаграма; одне рішення з виміром; тести й CI зелені |
| чесність і план | 10 | факти відділені від припущень; наступні кроки вимірювані |
| подача | 20 | 5–7 хвилин; великий шрифт; відповіді на питання |

## Що можна пропустити { #skip }

- **Крок 0** — для групи, яка вже писала HTTP-клієнти чи сервери.
- **Крок 6** — якщо в класі немає доступу до AI-агента; RSS-джерело кроку 6 можна взяти готовим, а лабу 1 зробити руками.
- **Живий LLM і живий бот** (кроки 7 і 9) — демонстрація у викладача; студенти працюють з `FakeLLM` і двійником
  Telegram, і всі тести від цього не залежать.
- **Деплой на сервер** (крок 11) — показати один раз; студентам достатньо `docker compose up --wait` локально.
- **Публікація образу в ghcr.io** (крок 12) — потребує власного форку; без неї решта CI працює.
