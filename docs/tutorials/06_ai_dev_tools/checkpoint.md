## Практика { #practice }

### Розібраний приклад: HTML-сторінка замість RSS { #worked-example }

Сайт іноді віддає замість стрічки сторінку помилки чи капчі — з кодом `200`. Що зробить `parse_pravda_rss`?

```python
from news_hub.rss import parse_pravda_rss

print(parse_pravda_rss("<html><body><h1>403 Forbidden</h1></body></html>"))
print(parse_pravda_rss("<rss><channel></channel></rss>"))
```

```text
[]
[]
```

Порожня стрічка й сторінка помилки дають однаковий результат — `[]`. Помилку ніхто не побачить: збір «успішний», новин 0. Правильний XML — не обов'язково RSS: `ET.fromstring` розбирає HTML-сторінку без помилки, а `root.iter("item")` просто нічого не знаходить. Ні специфікація, ні рецензія цього випадку не питали.

1. **Тест спершу.** HTML → `ValueError`; `<rss><channel></channel></rss>` → `[]` (порожня стрічка — легальний стан):

    ```python title="tests/unit/test_pravda_not_rss.py"
    import pytest

    from news_hub.rss import parse_pravda_rss


    def test_html_page_instead_of_rss_raises() -> None:
        with pytest.raises(ValueError, match="очікуємо RSS"):
            parse_pravda_rss("<html><body><h1>403 Forbidden</h1></body></html>")


    def test_empty_channel_is_empty_list() -> None:
        assert parse_pravda_rss("<rss><channel></channel></rss>") == []
    ```

    На коді кроку тест падає — так і має бути:

    ```text
    E       Failed: DID NOT RAISE ValueError
    FAILED tests/unit/test_pravda_not_rss.py::test_html_page_instead_of_rss_raises
    1 failed, 1 passed in 0.10s
    ```

2. **Код.** Після `ET.fromstring` перевірити корінь:

    ```python title="news_hub/rss.py (розв'язок)"
        if root.tag != "rss" or root.find("channel") is None:
            raise ValueError(f"очікуємо RSS (<rss><channel>), а отримали <{root.tag}>")
    ```

    ```text
    $ pytest -q -p no:cacheprovider
    109 passed in 4.73s
    $ mypy --strict news_hub
    Success: no issues found in 13 source files
    ```

    Тепер HTML-сторінка дає зрозумілу причину:

    ```text
    ValueError: очікуємо RSS (<rss><channel>), а отримали <html>
    ```

3. **Перевір, що тест ловить помилку:** прибери перевірку — тест має знову впасти з `DID NOT RAISE`.

`ValueError` — той самий виняток, що на битий XML: той, хто викликає парсер, обробляє обидва випадки однаково і бачить причину.

### Знайди помилку: тест, що закріплює помилку { #find-bug }

Код і тест із запуску A — агент написав їх разом, тест зелений:

```python title="запуск A: parser.py і tests/unit/test_parser.py (фрагменти)"
def parse_pravda_rss(xml: str) -> list[RawNews]:
    """RSS-стрічка Української правди (`/rss/view_news/`) → список сирих новин у форматі RawNews."""
    try:
        root = ET.fromstring(xml)
    except ET.ParseError:
        return []
    ...


def test_pravda_rss_broken_xml_is_empty_list() -> None:
    assert parse_pravda_rss("не xml") == []
```

Тест проходить і покриває гілку `except` — покриття 100%. Що не так і з кодом, і з тестом?

??? success "Відповідь"

    Код ковтає помилку: зламана стрічка, обрізана відповідь, HTML замість XML — усе стає «порожньою стрічкою». Коли RSS під'єднають до збору, такий збір виглядатиме успішним: новин 0, помилки немає. Сигналу, що джерело зламалось, не буде ніколи. Це «Errors should never pass silently» з Zen of Python навпаки — і порушення правила `CLAUDE.md` «відхилене — не мовчки».

    Тест це **закріплює**: агент написав його з тим самим припущенням, що й код, тож тест перевіряє реалізацію, а не вимогу. Очікуване значення має братися з вимог, а не з коду. Специфікація запуску B вимагала `ValueError` (`test_broken_xml_raises_value_error`) — і агент B зробив саме так. Висока цифра покриття тут нічого не означає: рядок виконано, але правильність не перевірено.

### Знайди помилку: «спрощені» дозволи { #find-bug-permissions }

Щоб агент менше питав, у `.claude/settings.json` замінили дозволи на такі:

```json
{
  "permissions": {
    "allow": ["Bash(git *)", "Bash(pip *)", "Edit"],
    "deny": ["Bash(rm -rf *)"]
  }
}
```

Що тепер може зробити агент без жодного запиту? Знайди три проблеми.

??? success "Відповідь"

    1. **`Bash(git *)` дозволяє `git push`** — і `git reset --hard`, `git push --force`. У кроці `git push` — у `deny`, і `deny` сильніший за `allow`. Тут `deny` для нього немає.
    2. **`Bash(pip *)` дозволяє `pip install` будь-чого**, зокрема вигаданого пакета з подібною назвою. У кроці — `deny: Bash(pip install *)`: нова залежність — лише через людину.
    3. **`Edit` без обмежень — і без `ask: Edit(./tests/**)`.** Агент змінить тести, щоб вони пройшли, і ніхто цього не помітить до рецензії. Плюс зникли `deny: Read(./.env)` і `WebFetch`: секрети потрапляють у контекст, а чужі сторінки — джерело промпт-ін'єкцій.

    Бонус: `deny: Bash(rm -rf *)` — «чорний список», який обходиться `/bin/rm -rf …` чи `python -c "…"`. Безпечніше дозволяти конкретне (`pytest`, `mypy`, `git diff`), ніж забороняти небезпечне за шаблоном.

## Підсумок { #summary }

| Поняття | Що запам'ятати |
|---|---|
| AI-агент | сам редагує й запускає команди в циклі «дія → перевірка»; якість залежить від того, чим він може себе перевірити |
| `CLAUDE.md` | команди перевірки й правила, яких не видно з коду; контекст, а не гарантія; застарілий — шкодить |
| permissions | `deny` > `ask` > `allow`; `allow` з репозиторію — лише після довіри до папки |
| hook | перевірка, яку агент не може «забути»; код 2 — агент мусить виправити; не межа безпеки |
| skill | повторюваний порядок роботи як команда `/…`; `$ARGUMENTS`, `` !`команда` `` |
| специфікація | фікстура + тести до коду, які падають; «не змінюй тести»; «перелічи рішення, які ухвалив сам» |
| рецензія | діф тестів, дані агента, «що буде, якщо…», мінімальні версії й інші ОС; кожна знахідка — тест, що падає на коді агента |
| ризик AI-коду | не падіння, а правдоподібна неправда: зелені тести, гарний графік, неправильні дані |

## Самоперевірка { #self-check }

1. Чим `CLAUDE.md` відрізняється від `permissions.deny`? Наведи правило, яке має бути в `deny`, а не лише в `CLAUDE.md`.
2. Чому `allow` з `.claude/settings.json` не діяв у першому запуску, а hook — діяв?
3. Що hook отримує на stdin і що означає його код виходу `2`?
4. Запуск A — 101 зелений тест. Чому це не доводить, що код правильний?
5. Що дала специфікація запуску B і чого вона не дала?
6. Чому `pubDate` у GMT перетворився на `17:05` замість `20:05`, і чому фікстура лише з `+0300` цього не показує?
7. Навіщо тест рецензента на `tzdata`, якщо на Linux є системна база поясів?
8. Чому `jsonify` зіпсував «топ-ознаки» без жодної помилки? Що об'єднує всі десять вад того проєкту?

??? success "Відповіді"

    1. `CLAUDE.md` — контекст: агент зазвичай виконує, але може не виконати. `deny` — межа: дію не буде виконано, хоч би що вирішив агент. `Read(./.env)`, `Bash(git push *)`, `Bash(pip install *)` — у `deny`.
    2. `allow`-правила з файлу репозиторію діють лише після того, як людина довірила папку; `claude -p` діалог довіри пропускає. `deny`, `ask` і hooks діють без цього кроку.
    3. JSON події: `tool_name` і `tool_input.file_path`. Код `2` після `PostToolUse` — правку вже зроблено, але stderr (хвіст виводу `pytest`) іде агентові як помилка, яку треба виправити.
    4. Тести написав той самий агент на вигаданих ним даних: вони перевіряють його припущення (лише `+0300`, `[]` на битих даних), а не вимоги.
    5. Дала: перевірний критерій готовності, 2 файли замість 10, незмінені тести, названі рішення, удвічі менше часу й грошей. Не дала: випадків, про які специфікація мовчала (немає `<category>`, битий `<pubDate>`, Windows без `tzdata`), — їх знайшла рецензія.
    6. Пояс відкинули (`replace(tzinfo=None)`), не перевівши час у київський (`astimezone`). Для `+0300` цифри в рядку вже київські — помилка не видна; видно її лише на даті з іншим поясом.
    7. Щоб `requirements.txt` казав правду: на Windows без `tzdata` `news_hub.rss` не імпортується взагалі. Тест імітує Windows через `PYTHONTZPATH` і падає в будь-якому оточенні без `tzdata` — навіть на Linux.
    8. Flask за замовчуванням сортує ключі JSON за алфавітом; словник, відсортований за важливістю, приходив у клієнт за абеткою, а UI брав перші 12. Усі десять вад не падають з помилкою: застосунок працює й показує правдоподібний, але неправильний результат.
